# A3S Code 能力边界

A3S Code 会把关键 runtime 决策明确展示出来。工具可以保留在 Executor 中，但不必在
每个 Turn 都发送给模型；高风险调用可以在副作用发生前暂停；远程执行只在登录后
注册；历史上下文则通过显式且有边界的命令恢复。

这些是相互独立的控制层，而不是一个笼统的“Agent 模式”。

| 能力              | 控制什么                                        | 不负责什么                                                                     |
| ----------------- | ----------------------------------------------- | ------------------------------------------------------------------------------ |
| Code Intelligence | 对 saved files 执行只读语义 symbols、导航和诊断 | 不编辑文件，也不执行 refactor。参见 [Code Intelligence](./code-intelligence)。 |
| Human in the loop | 一个越过边界的精确调用是否可以继续              | 不会把隐藏工具自动变安全，也不会授予宽泛的 shell wildcard。                    |
| 渐进式工具 API    | 当前 Turn 中哪些已注册 schema 会进入模型上下文  | 它控制 context disclosure，不负责授权。                                        |
| `runtime`         | 登录后把独立任务提交给远程 Batch                | 登出时不可见，并且调用仍需要确认。                                             |
| `/ctx`            | 显式检索历史会话，并可选择保存                  | 历史文本只是参考，不是可信指令。                                               |

## Human in the loop

调用需要授权时，A3S Code 会在副作用发生前暂停精确调用，并展示四种选择：

1. **仅允许一次**
2. **本会话允许该精确能力**
3. **把精确能力规则写入项目**
4. **拒绝并告诉 Agent 原因**

例如授权界面会把操作明确显示为 `Bash(git push origin main)`。选择“仅允许一次”只会
恢复这一笔调用。项目规则仍是精确规则，而且在 ACL 写入成功前工具会保持暂停。拒绝
时可以把替代方案作为新指引交还给 Agent。

HITL 是统一 invocation path 中的一环：

```text
模型发出 tool call
  → mode 与 permission policy
  → 工具自身的确认要求
  → 用户对精确调用做决定
  → budget、timeout、cancellation、hooks 与结果清洗
```

非交互 Auto 模式无法询问用户，因此需要授权的操作会被拒绝，而不是静默继续。

## 渐进式工具 API 披露

Executor 始终保留完整的工具注册表。在每个模型 Turn 之前，A3S Code 决定哪些定义
需要进入本轮上下文：

- 常规编码任务始终保留核心 repository tools：文件读写、搜索、shell、Code
  Intelligence、任务委派与 skill discovery。
- Web、fetch、Git、batch、program 和 MCP definitions 会在最近的文本意图需要时加入。
- 单独的问候语不会收到任何 tool definitions。
- 选择器会检查最近的非工具文本，因此简短追问仍能继承当前任务意图。

例如“测试通过后提交 parser 修复”这一请求中，Executor 仍然拥有所有工具；模型只会
收到核心编码 schemas 和 Git。Web、batch、program 与无关 MCP schemas 保持延后。

它减少的是重复 schema token，**不会**绕过 permission、HITL、timeout、
cancellation 或工具自身的确认要求。

## 登录后注册的 `runtime` 工具

只有 `/login` 建立有效平台会话后，`runtime` 才会进入动态工具注册表。登出时会移除，
因此未登录模型看不到也无法调用它。

Schema 中有两个必填参数：

| 参数         | 类型                  | 必填 | 契约                                                          |
| ------------ | --------------------- | ---- | ------------------------------------------------------------- |
| `tasks`      | string 或 object 数组 | 是   | 一个或多个可以并行执行的独立输入。                            |
| `worker`     | string                | 是   | tool-kind agent asset 的 UUID 或名称；名称会在提交前解析。    |
| `timeout_ms` | integer               | 否   | 等待完整 Batch 的上限，默认 10 分钟；超时后仍保留已完成结果。 |

```json
{
  "tasks": ["审查依赖风险", "梳理升级路径", "起草发布说明"],
  "worker": "release-research",
  "timeout_ms": 300000
}
```

远程任务可能产生成本或外部副作用，因此该工具始终要求确认。批准后，它会：

1. 在需要时解析 Worker 名称。
2. 用 idempotency key 把所有输入提交为一个远程 Batch。
3. 流式展示 queued、running 与 done 数量，同时不阻塞 Batch。
4. 用有界退避轮询，并容忍短暂网络失败。
5. 并发收集已经完成的输出。

重试会重新连接同一个 Batch，而不会重复消耗。Budget 到期时，结果会明确返回
`partial: true`、已经完成的子集，以及可供后续检查的 Batch ID。

## `/ctx` 跨会话上下文

`/ctx` 是历史 coding-agent 会话的显式召回入口：

| 命令            | 结果                                                            |
| --------------- | --------------------------------------------------------------- |
| `/ctx <query>`  | 搜索历史会话，最多展示 8 个可编号选择的结果。                   |
| `/ctx <n>`      | 拉取第 `n` 条结果的有界 transcript window，只暂存给下一条消息。 |
| `/ctx save <n>` | 把选中结果保存为长期记忆，并保留 event/session provenance。     |

示例：

```text
/ctx 为什么 auth refresh 会失败？
/ctx 1
```

第二条命令不会永久扩张当前 conversation。它只把窗口附加到下一条消息一次，随后清空
暂存内容。需要长期保留时，使用显式的 `/ctx save 1`。

### 历史文本是不可信输入

历史 tool output 可能包含过时代码，甚至带有类似 prompt injection 的文本。因此 A3S
Code 会：

- 去除 control 与 ANSI sequences；
- 把注入窗口限制为 6000 bytes；
- 为每一行添加 quote prefix，避免嵌入的 fence 逃逸历史区块；
- 明确标注这是 untrusted reference material；
- 保存结果时保留 `ctx_event_id` 和 `ctx_session_id`。

Agent 在采取行动前，仍应使用当前 workspace 验证召回的历史决策。

## 这些能力如何组合

同一个编码任务可以依次使用这些边界，而不把它们混为一谈：

```text
/ctx 找回历史决策
  → Code Intelligence 定位当前语义目标
  → 渐进式披露保持本轮 schema 聚焦
  → HITL 暂停一个精确的外部副作用
  → 登录后由 runtime 并行执行已批准的独立任务
```

每一层都保持可观测、有边界，并且可以独立测试。
