## 嵌入式推理库

`embedded-inference` feature 是模型无关的 Rust 库路径，与 HTTP server 和
`Backend` registry 分离。它不会启动进程、监听端口或下载模型。模型所属 crate 负责
graph execution、tokenizer、preprocessing、postprocessing 与 revision policy；Power
提供共享的设备和权重运行时。

Power 0.6.0 深化了借鉴 Colibri 的运行时机制，同时不再建设第二套 cache 或安全平面：

- 精确的 SafeTensors inventory 与完整性校验；
- storage、host、device 三层驻留，以及 LFRU/LRU heat；
- 原子 hot-plan 替换与批量 expert-union 规划；
- 带 useful/unused byte 统计的有界 prefetch；
- 完整或精确子集的加权只读副本，以及 validation throughput weighting 和已校验 fallback；
- 基于 usage ranking 的部分 mirror 规划与 staging：仅选择完整且已校验的 SafeTensors
  文件，遵守显式 byte budget 与 free-space reserve，复用精确文件，并以原子 no-replace
  方式发布；
- 可选的 Linux、macOS、Windows、CUDA、Metal 原生容量探测，以及基于调用方显式
  fraction、reserve、cap 与 host/device allocation order 的确定性 cache budget；
- 有界请求准入、取消、隐私安全 telemetry 与规范 execution receipt；
- 既有 TEE、attestation、完整性与隐私不变量。

自动预算不会改变默认零 cache，也不会启动 `nvidia-smi`、`vm_stat` 或其它辅助进程。
Metal unified memory 只作为一个共享池计量，不会同时重复计入 host 与 device。硬件快照
与派生 plan 只作为显式 operator value 返回。部分 mirror 默认拒绝明文目标；调用方必须
显式承担该 confidentiality 决策，且每个选中文件都会与已校验的 primary descriptor
复核。Power 不会自动记录或持久化硬件快照、派生 plan、mirror path、usage heat 或 stage
report，也不会将它们导出到 placement telemetry 或绑定到 execution receipt，因此
Colibri 风格的内存层级仍位于同一套 TEE 与完整性平面内。

精确 positional/direct tensor read 与独立 cold-storage A/B 仍由
[Power issue #19](https://github.com/A3S-Lab/Power/issues/19) 跟踪。Power 0.6.0
不声称已经获得这些 benchmark 结果，也不会默认启用 direct I/O。

A3S OCR 0.5.0 使用 Power 0.6.0 执行 Rust PP-OCRv6 和 Unlimited-OCR，但 Power
不内置任何一个模型。OCR 只在延迟加载模型 session 时选择同一个 typed residency
budget；Parser 只转发 host policy，不实现另一套硬件或 mirror planner。嵌入式依赖闭包
不包含 Power server、HTTP client、ONNX Runtime 或 browser automation。完整 ownership
与 parity contract 见
[嵌入式推理架构](https://github.com/A3S-Lab/Power/blob/main/docs/embedded-inference-architecture.md)。

## 对话补全

```bash
# 非流式
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llama3.2:3b",
    "messages": [
      {"role": "system", "content": "你是一个有帮助的助手。"},
      {"role": "user", "content": "什么是 Rust？"}
    ]
  }'

# 流式（逐 token SSE）
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llama3.2:3b",
    "messages": [{"role": "user", "content": "你好！"}],
    "stream": true
  }'
```

流式模式下每生成一个 token 即通过 SSE（`data: {...}`）推送，生成完成后发送 `data: [DONE]`。

```bash
  -d '{
    "model": "llava:7b",
    "messages": [{"role": "user", "content": "这张图片里有什么？"}],
    "images": ["iVBORw0KGgoAAAANSUhEUgAA..."]
  }'

# OpenAI 风格的 image_url 内容部分
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "llava:7b",
    "messages": [{
      "role": "user",
      "content": [
        {"type": "text", "text": "描述这张图片"},
        {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,/9j/4AAQ..."}}
      ]
    }]
  }'
```

支持的图片格式：JPEG、PNG、WebP。

## 对话模板

Power 使用 Jinja2（通过 `minijinja`）渲染对话模板。模板从 GGUF 元数据中读取，也可通过模型 manifest 的 `template_override` 字段覆盖。

支持格式：ChatML、Llama 3、Mistral、Gemma、Phi 及自定义 Jinja2 模板。

## KV 缓存复用

当新请求与之前的请求共享前缀（相同系统提示 + 对话历史）时，复用已缓存的 KV 状态，无需重新计算。对多轮对话和重复系统提示有显著加速效果。

## 思维链 / 推理模型

DeepSeek-R1、QwQ 等推理模型会输出 `<think>...</think>` 块。Power 的流式解析器将思维内容与最终响应分离，分别作为独立 chunk 推送。

## 层流式推理（picolm）

传统 LLM 推理在生成第一个 token 之前需要将整个模型加载到内存中。一个 7B Q4_K_M 模型需要约 4 GB 内存。而在 TEE 中，加密页面缓存（EPC）通常限制在 512 MB–1 GB。模型根本放不下。

picolm 通过层流式推理解决这个问题：不是一次性加载所有权重，而是通过 mmap 映射 GGUF 文件，逐层处理 transformer 层。任何时刻只有当前层的权重占用物理内存。

### 工作原理

实现由两个组件构成：

**`gguf_stream.rs` — 零拷贝 GGUF 解析器**：通过 `mmap(PROT_READ)` 打开 GGUF 文件，解析头部和张量描述符，但不加载任何权重数据。当 picolm 请求某层的权重时，`tensor_bytes(name)` 直接返回 mmap 区域的 `&[u8]` 切片——零拷贝、零分配。操作系统按需换入数据页，在内存压力下自动回收。

**`picolm.rs` 与 `picolm_ops/` — 层流式前向传播**：依次遍历每个 transformer 层（`blk.0.*` 到 `blk.{n-1}.*`），执行 attention、feed-forward、normalization、RoPE、KV cache、采样、grammar 与工具调用逻辑，然后继续下一层。处理完第 N 层后，通过 `madvise(MADV_DONTNEED)` 释放其映射页面，再换入第 N+1 层。

### 内存对比

| 模型 | 传统方式 | picolm 层流式 | 降幅 |
|------|---------|--------------|------|
| 3B Q4_K_M (~2 GB) | ~2 GB | ~60 MB + KV | 33× |
| 7B Q4_K_M (~4 GB) | ~4 GB | ~120 MB + KV | 33× |
| 13B Q4_K_M (~7 GB) | ~7 GB | ~200 MB + KV | 35× |
| 70B Q4_K_M (~40 GB) | ~40 GB | ~1.1 GB + KV | 36× |

### 加密模型支持

对于加密模型（`.enc`），`streaming_decrypt = true` 使用 `LayerStreamingDecryptedModel`：完整明文会一次性解密到 `mlock` 锁定内存，drop 时清零，并通过包装在 `Zeroizing<Vec<u8>>` 中的 chunk 读取接口暴露。picolm 可以按层处理这些 chunk，因此只有当前工作副本需要跨层保留。AES-256-GCM 具备认证加密能力，但不支持按层随机解密；该模式的目标是不写明文磁盘并限制活跃工作集，而不是让密文按层可随机访问。

### 已实现的前向路径

picolm 是已实现的纯 Rust 推理路径，不是占位实现。当前源码包含：

- 支持 Grouped-Query Attention（GQA）和 Q/K/V bias 的多头注意力。
- SwiGLU 与 GeGLU feed-forward 变体。
- RoPE 表、RMSNorm、FP16 KV cache，以及融合 f16 dot/accumulate 路径。
- Q4_K、Q5_K、Q6_K、Q8_0、Q4_0、F16、F32 dequantization。
- 融合 dequant+dot 内核、Rayon 并行 matmul、aarch64 NEON 与 x86_64 AVX2 热路径。
- 批量 prefill、JSON grammar 约束输出、工具调用解析和可选 speculative-decoding 模式。
- 在加载 picolm 模型前运行关键数值内核 startup self-test。

## 自动加载

当请求到达时，若目标模型尚未加载，Power 会自动加载它。若已达 `max_loaded_models` 上限，最近最少使用的模型会被先驱逐。
