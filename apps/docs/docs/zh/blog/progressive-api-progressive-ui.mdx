# 渐进式 API 与渐进式 UI：按需发现能力，让结果长出界面

<BlogMeta />

智能体接入一个系统时，最直接的做法是把整份 OpenAPI、全部工具 schema 和所有页面
一次性交给模型。系统越大，这种办法越快失效：上下文被大量无关契约占满，权限边界
难以看清，接口升级会放大提示词漂移，模型还可能在没有读懂参数约束前就尝试写操作。

A3S 使用两条相互配合的渐进路径：

- **渐进式 API**：先搜索能力，再读取一个操作的准确契约，最后执行；
- **渐进式 UI**：只有当执行结果确实需要交互界面时，响应才附带一个受约束的
  `view`，由已经登录的宿主打开。

核心不是把 API 或 UI 变得“动态”这么简单，而是让发现、契约、执行和呈现都发生在
恰当的时刻，并继续经过同一套身份、权限和审计边界。

## 一个端点，四个动作

A3S OS 把可发现能力投影到一个入口：

```text
POST /api/v1/kernel/capabilities
```

请求通过 `action` 逐步收窄：

```text
list → search → describe → execute
```

| 动作 | 回答的问题 | 建议保留的结果 |
| --- | --- | --- |
| `list` | 当前身份能看到哪些模块？ | 模块名与简短说明 |
| `search` | 哪些操作可能完成这项任务？ | 少量候选操作及匹配信息 |
| `describe` | 这个操作准确需要什么？ | method、path、参数 schema 与呈现提示 |
| `execute` | 按已读契约执行后发生了什么？ | 业务数据、trace，以及可选的 `view` |

这不是隐藏真实 API。它是位于真实模块和操作之前的一层**按权限过滤的能力索引**。
发现结果不授予新权限，`execute` 仍然使用当前登录身份完成最终鉴权。

## 为什么要渐进展开

传统的“一次加载全部工具”把四种不同职责混在一起：目录、检索、类型契约和执行。
渐进式 API 把它们重新拆开。

1. **上下文保持有界。** 模型先拿到模块或少量候选，不需要背着整个平台的 schema。
2. **执行前读契约。** `describe` 把参数、操作和呈现能力固定在当前版本的真实返回上。
3. **权限与发现一致。** 用户看不到的模块不会因为写在公共提示词里而泄漏出来。
4. **升级更稳。** 客户端搜索意图并读取当前契约，而不是长期猜测某个内部操作名。
5. **审计更清楚。** 搜索、描述和执行可以分别留下 `requestId` 与时间戳。

因此，正确路径不是“猜中一个操作名然后调用”，而是从宽到窄：

```text
用户意图
  └─ search：找到少量候选
       └─ describe：确认输入契约
            └─ execute：提交参数
                 ├─ data：机器可读结果
                 └─ view：可选的渐进式 UI
```

## 开始使用

先登录 A3S OS，再进入 A3S Code：

```bash
a3s auth login os
a3s code
```

登录后的 Code 会把 `A3S_OS_BASE_URL` 和短期访问令牌安全地注入其工具环境。不要在
对话、日志或脚本输出里打印 `A3S_OS_TOKEN`。下面的 `curl` 示例假设它们已经存在于
当前受信任的环境。

### 1. 列出模块

当你还不知道系统范围时，从 `list` 开始：

```bash
curl --fail-with-body --silent --show-error \
  --request POST "$A3S_OS_BASE_URL/api/v1/kernel/capabilities" \
  --header "Authorization: Bearer $A3S_OS_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"action":"list"}'
```

列表用于建立边界，不适合整份复制回模型上下文。可以用 `jq` 只提取模块名和摘要。

### 2. 按意图搜索

查询应该描述目标，而不是预先猜测 controller 或 route：

```bash
curl --fail-with-body --silent --show-error \
  --request POST "$A3S_OS_BASE_URL/api/v1/kernel/capabilities" \
  --header "Authorization: Bearer $A3S_OS_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "action": "search",
    "query": "deploy an application agent and retain operation status"
  }'
```

保留最相关的少量候选即可。即使某个操作名以前可用，也应重新搜索，因为部署版本、
权限和模块注册状态都可能变化。

### 3. 描述一个操作

从搜索结果中选择候选，再读取准确契约：

```json
{
  "action": "describe",
  "module": "<module from search>",
  "operation": "<operation from search>"
}
```

在执行前检查必填字段、字段类型、枚举、超时、幂等键以及操作的写入边界。不要把旧文档
里的参数结构强行套到新的 `describe` 结果上。

### 4. 执行，并保留完整响应

参数必须服从刚读到的契约。需要宿主呈现界面时加入 `"shaped": true`：

```json
{
  "action": "execute",
  "module": "<described module>",
  "operation": "<described operation>",
  "shaped": true,
  "params": {
    "<required field>": "<value>"
  }
}
```

`execute` 的返回已经是紧凑结果，不要再用 `jq` 把它裁成单个 data 字段。否则即使操作
返回了 `view`，宿主也看不到它。面向用户的总结应简短，同时保留响应中的
`requestId` 与 `timestamp` 作为追踪依据。

## 渐进式 UI 是执行结果，不是第二套前端协议

数据足以表达结果时，API 只返回数据。操作需要查看日志、审批、检查部署状态或继续
交互时，shaped 响应可以增加：

```json
{
  "success": true,
  "data": {
    "operationId": "c7a4…f103",
    "status": "pending"
  },
  "view": {
    "url": "/admin/operations/c7a4…f103?embed=1",
    "width": 1120,
    "height": 760
  },
  "requestId": "…",
  "timestamp": "2026-07-31T00:00:00.000Z"
}
```

这里的 `view` 是一个呈现建议，而不是权限凭证：

- URL 通常是相对于已登录 A3S OS origin 的根路径；
- TUI 在可信边缘把它补全为绝对 `http(s)` URL；
- `width` 与 `height` 是弹窗建议尺寸，不改变授权；
- A3S Code 检测到 `view` 后显示 **Open view**，再由认证过的 WebView 或浏览器打开；
- 没有 `view` 时，文本和结构化数据路径仍然完整可用。

这就是“渐进式”的含义：UI 不需要预先占据主工作区，也不要求每个 API 都造一页。
它只在某次结果需要更丰富的呈现时出现，并且继续绑定同一个 origin 和登录会话。

## 宿主如何接入 shaped view

自定义宿主可以遵循与 A3S Code 相同的最小规则：

1. 完整解析 `execute` JSON，并递归寻找当前 `view`；兼容旧服务时可回退到
   `viewUrl`、`viewSize` 和 `embeddable`。
2. 根相对 URL 只能与已登录、受信任的 OS origin 组合。
3. 只接受 `http://` 或 `https://`；拒绝 `file:`、`javascript:` 和无 origin 的
   相对路径。
4. 多个连续结果里选择最新的 view，避免打开过时界面。
5. 让用户主动点击打开，不把原始带状态 URL输出到对话。
6. 视图关闭后，持久业务状态仍以 API 返回的 ID 和后续查询为准。

渐进式 UI 因而是一种**宿主与结果之间的窄契约**，不是让远端页面接管宿主导航、
凭据或本地文件系统。

## 一个完整例子：从部署意图到可操作视图

A3S 首页展示的 Cloud 路径可以概括为：

1. 在 Code 中完成并检查 Agent；
2. `search` 查找部署 application Agent 的能力；
3. `describe` 读取当前部署操作的输入 schema；
4. `execute` 提交参数并设置 `shaped: true`；
5. Cloud 返回 `workloadId`、`revisionId` 和持久 `operationId`；
6. Flow 继续 operation，Runtime 与 Box 收敛 Service，Gateway 只接入健康 revision；
7. 返回的 view 打开 operation 页面，用户查看进度、日志或后续动作。

终端不需要保持一个长连接来“拥有”部署。持久 ID 负责机器工作流，view 负责当下的人机
交互；两者来自同一次受审计执行，却各自保持清晰职责。

## 常见问题

### 执行成功但没有 Open view

先检查请求是否包含 `"shaped": true`，以及完整 `execute` 响应是否被保留。`jq` 只取
`.data` 会删除 `.view`。如果响应本来就没有 view，说明该操作只提供数据结果；这不是
错误。

### 搜索不到操作

把查询改成目标、对象和动作的组合，避免只写某个旧 route 名。仍无结果时，检查当前
账号权限和模块是否已注册。

### 参数突然不再通过校验

重新执行 `describe`。渐进式客户端应把当前契约视为权威，而不是缓存旧 schema 后无限
复用。

### view URL 不能打开

确认宿主拥有登录时的可信 origin，并且没有把根相对 URL 当成本地文件路径。不要为了
“修复”它而放开任意 scheme 或任意远端 origin。

## 什么时候适合使用

渐进式 API/UI 特别适合能力很多、权限因人而异、操作 schema 会演进，且部分结果需要
人工检查的系统。对于只有两三个固定函数的内部库，直接使用类型化 SDK 往往更简单。

判断标准不是“能不能把所有东西做成一个 endpoint”，而是：调用者是否会因为先发现、
再读契约、最后执行而获得更小的上下文和更清楚的权限边界；用户是否会因为界面按结果
出现，而不必提前进入一个庞大控制台。
