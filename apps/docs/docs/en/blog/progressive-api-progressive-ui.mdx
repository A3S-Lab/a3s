# Progressive API and Progressive UI: Discover Capabilities on Demand, Grow Interfaces From Results

<BlogMeta />

The most direct way to connect an agent to a system is to give the model the
entire OpenAPI document, every tool schema, and every page up front. The larger
the system becomes, the faster that approach breaks down. Irrelevant contracts
consume context, authorization boundaries become hard to see, interface changes
amplify prompt drift, and the model may attempt a write before it understands the
input contract.

A3S uses two progressive paths that work together:

- a **Progressive API** searches for a capability, reads one exact operation
  contract, and only then executes it;
- a **Progressive UI** appears only when an execution genuinely benefits from an
  interactive surface, delivered as a constrained `view` in the result and
  opened by the authenticated host.

The point is not merely to make APIs or interfaces “dynamic.” Discovery,
contracts, execution, and presentation should happen at the right time while
remaining inside the same identity, permission, and audit boundary.

## One endpoint, four actions

A3S OS projects discoverable capabilities through one entrypoint:

```text
POST /api/v1/kernel/capabilities
```

The request narrows through the `action` field:

```text
list → search → describe → execute
```

| Action | Question it answers | Result worth retaining |
| --- | --- | --- |
| `list` | Which modules can this identity see? | Module names and short summaries |
| `search` | Which operations might satisfy this intent? | A few candidate operations and match evidence |
| `describe` | What exactly does this operation require? | Method, path, parameter schema, and presentation hints |
| `execute` | What happened after applying the reviewed contract? | Business data, trace fields, and an optional `view` |

This does not conceal the real APIs. It is a **permission-filtered capability
index** in front of real modules and operations. Discovery grants no additional
authority; `execute` still performs final authorization as the signed-in user.

## Why reveal the system progressively

The “load every tool at once” pattern mixes four different responsibilities:
catalog, retrieval, type contracts, and execution. A Progressive API separates
them again.

1. **Context stays bounded.** The model receives modules or a few candidates,
   not the schema for the whole platform.
2. **The contract is read before execution.** `describe` grounds parameters and
   presentation behavior in the current deployment.
3. **Discovery matches authorization.** A module the user cannot see does not
   leak through a shared system prompt.
4. **Upgrades are less brittle.** Clients search by intent and inspect the
   current contract instead of guessing a long-lived internal operation name.
5. **Auditing is clearer.** Search, description, and execution can each retain a
   `requestId` and timestamp.

The correct path is therefore broad to narrow, not “guess a name and call it”:

```text
user intent
  └─ search: resolve a few candidates
       └─ describe: inspect the input contract
            └─ execute: submit validated parameters
                 ├─ data: machine-readable result
                 └─ view: optional Progressive UI
```

## Start using it

Sign in to A3S OS, then enter A3S Code:

```bash
a3s auth login os
a3s code
```

The signed-in Code host injects `A3S_OS_BASE_URL` and a short-lived access token
into its tool environment. Never print `A3S_OS_TOKEN` into a conversation, log,
or script output. The following `curl` examples assume those variables already
exist in a trusted environment.

### 1. List modules

Start with `list` when the platform boundary is unknown:

```bash
curl --fail-with-body --silent --show-error \
  --request POST "$A3S_OS_BASE_URL/api/v1/kernel/capabilities" \
  --header "Authorization: Bearer $A3S_OS_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{"action":"list"}'
```

The list establishes scope; it is not meant to be pasted wholesale back into
model context. Use `jq` to retain only module names and short summaries.

### 2. Search by intent

Describe the objective instead of guessing a controller or route:

```bash
curl --fail-with-body --silent --show-error \
  --request POST "$A3S_OS_BASE_URL/api/v1/kernel/capabilities" \
  --header "Authorization: Bearer $A3S_OS_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "action": "search",
    "query": "deploy an application agent and retain operation status"
  }'
```

Keep only a few strong candidates. Search again even if an operation name worked
before: deployment versions, permissions, and module registration can change.

### 3. Describe one operation

Select a candidate from search and request its current contract:

```json
{
  "action": "describe",
  "module": "<module from search>",
  "operation": "<operation from search>"
}
```

Before execution, inspect required fields, types, enums, timeout controls,
idempotency keys, and the operation's write boundary. Do not force an old
documentation shape onto a newer `describe` result.

### 4. Execute and preserve the whole response

Parameters must follow the contract just reviewed. Add `"shaped": true` when
the host should retain presentation data:

```json
{
  "action": "execute",
  "module": "<described module>",
  "operation": "<described operation>",
  "shaped": true,
  "params": {
    "<required field>": "<value>"
  }
}
```

An `execute` response is already compact. Do not narrow it to one data field
with `jq`: doing so strips `view` even when the operation returned one. Summarize
the user-facing result briefly while retaining `requestId` and `timestamp` for
traceability.

## Progressive UI is an execution result, not a second frontend protocol

When data is sufficient, the API returns data. When an operation benefits from
log inspection, approval, deployment status, or continued interaction, a shaped
response can add:

```json
{
  "success": true,
  "data": {
    "operationId": "c7a4…f103",
    "status": "pending"
  },
  "view": {
    "url": "/admin/operations/c7a4…f103?embed=1",
    "width": 1120,
    "height": 760
  },
  "requestId": "…",
  "timestamp": "2026-07-31T00:00:00.000Z"
}
```

The `view` is a presentation hint, not a credential:

- its URL is normally root-relative to the signed-in A3S OS origin;
- the TUI completes it to an absolute `http(s)` URL at the trusted edge;
- `width` and `height` suggest popup dimensions but grant no authority;
- A3S Code shows **Open view**, then opens it with the authenticated WebView or
  browser path;
- without a `view`, the text and structured-data result remains fully usable.

That is what makes the UI progressive. It does not occupy the primary workspace
in advance, and every API operation does not need its own permanent page. A
richer interface appears only when this result needs one, bound to the same
origin and signed-in session.

## Integrating shaped views in another host

A custom host can follow the same narrow rules as A3S Code:

1. Parse the complete `execute` JSON and recursively locate the current `view`;
   when supporting older services, fall back to `viewUrl`, `viewSize`, and
   `embeddable`.
2. Resolve a root-relative URL only against the signed-in, trusted OS origin.
3. Accept only `http://` or `https://`; reject `file:`, `javascript:`, and a
   relative path with no origin.
4. If a command emitted multiple JSON results, select the newest view rather
   than opening stale UI.
5. Require an explicit user action to open it; do not print raw state-bearing
   URLs into the conversation.
6. After the view closes, durable business state remains identified by API IDs
   and subsequent queries.

Progressive UI is therefore a **narrow contract between a result and its host**.
It does not let a remote page take over host navigation, credentials, or the
local filesystem.

## End to end: deployment intent to an operable view

The Cloud path shown on the A3S homepage can be summarized as follows:

1. Build and verify the Agent in Code.
2. `search` for the capability that deploys an application Agent.
3. `describe` the current deployment input schema.
4. `execute` the reviewed operation with `shaped: true`.
5. Cloud returns a `workloadId`, `revisionId`, and durable `operationId`.
6. Flow continues the operation, Runtime and Box converge the Service, and
   Gateway admits only a healthy revision.
7. The returned view opens the operation page for progress, logs, and follow-up
   actions.

The terminal does not need to hold a long connection and “own” the deployment.
Durable IDs serve the machine workflow; the view serves the current human
interaction. Both come from one audited execution while keeping distinct jobs.

## Troubleshooting

### Execution succeeded but there is no Open view

Check that the request included `"shaped": true` and that the complete
`execute` response survived. Selecting only `.data` with `jq` removes `.view`.
If the original response has no view, the operation exposes a data-only result;
that is not an error.

### Search returns no operation

Express the query as an objective, object, and action rather than an old route
name. If it still returns nothing, check the current account's permissions and
whether the module is registered.

### Parameters suddenly fail validation

Run `describe` again. A progressive client treats the current contract as
authoritative instead of caching an old schema indefinitely.

### The view URL cannot open

Verify that the host retained the trusted origin from login and did not treat a
root-relative URL as a local file. Never “fix” the problem by permitting
arbitrary schemes or origins.

## When this pattern fits

Progressive API and UI fit systems with many capabilities, identity-dependent
visibility, evolving operation schemas, and results that sometimes need human
inspection. A typed SDK is usually simpler for an internal library with only a
few fixed functions.

The test is not “can everything be placed behind one endpoint?” It is whether
callers gain smaller context and clearer authority by discovering first,
reading the contract second, and executing last—and whether users benefit when
an interface appears from a result instead of making them enter a large console
up front.
