A3S Box 3.2 is a local OCI runtime, not a hosted Sandbox service. It ships a Docker-like CLI, local cross-language SDKs, CRI/containerd adapters, and the host and guest components that actually run a workload.

The older article led with “40 MB,” “200 ms,” and “a complete Docker replacement.” Those claims hid platform and feature conditions. The current contract is clearer: a dedicated-kernel MicroVM is the default; a shared-kernel Sandbox is selected only by an explicit request.

## Isolation classes never substitute for each other

| Contract | Default MicroVM | Explicit Sandbox |
| --- | --- | --- |
| Backend | libkrun | A3S OCI Runtime |
| Kernel | Dedicated guest Linux | Shared host Linux |
| Selection | Omit `--isolation` | `--isolation sandbox` |
| Primary use | Untrusted work and stronger tenant boundaries | Trusted or semi-trusted tools and tests |
| TEE / warm pool / snapshot-fork | Available on qualifying hosts | Rejected |
| Automatic fallback | Never | Never |

Box intentionally rejects `--isolation microvm`. Omitting the flag is the only public way to choose the default, preventing scripts from treating backend names as interchangeable compatibility modes.

```bash
# Default: MicroVM
a3s-box run --rm alpine:3.20 -- uname -a

# Explicit Sandbox on a Linux host that passes capability checks
a3s-box run --rm --isolation sandbox alpine:3.20 -- id
```

## Current runtime surface

The CLI covers:

- `run`, `create`, `start`, `stop`, `exec`, `attach`, logs, and health;
- OCI pull/push, builds, save/load, commits, and caches;
- bind mounts, volumes, tmpfs, snapshots, copy, and diff;
- TSI, named bridges, TCP publication, and a bounded Compose subset;
- warm pools and optional snapshot-fork on Linux/KVM;
- audit, metrics, events, security receipts, and SEV-SNP-oriented TEE flows.

Docker-like does not mean Docker API complete. Unsupported options fail before state changes instead of being stored and ignored.

## SDKs use the same local runtime

Rust, Python, TypeScript, and Go all operate the installed Box runtime and its state. They expose no remote endpoint, domain, or API-key configuration.

The 3.2 SDK bridge validates a 48-operation inventory before normal calls. Protocol-version or result-shape mismatches fail closed.

```python
from a3s_box import Sandbox

with Sandbox.create("python:3.12-alpine") as sandbox:
    result = sandbox.commands.run("python -c 'print(6 * 7)'")
    print(result.stdout)
```

A product that needs a remote Sandbox service should put an authenticated service in front of the local SDK. Box itself does not pretend to be a network control plane.

## Platform boundaries

| Path | Current state |
| --- | --- |
| Linux/KVM MicroVM | Primary path; a restricted-egress subset has passed real-host gates |
| Apple Silicon/HVF MicroVM | Implemented; a restricted-egress subset has passed real-host gates |
| Windows x86-64/WHPX | Implemented and soak-tested; one vCPU, without exec/PTY, bridge networking, TEE, snapshot-fork, or CRI |
| Linux Sandbox | Preview; shares the host kernel |
| Kubernetes | Preview; CRI v1 and a containerd runtime-v2 shim |
| TEE | SEV-SNP-oriented; TDX is not productized |

## How to read the Kubernetes evidence

The latest recorded `critest` baseline is from Box 2.2.0: 73 passed, 7 failed, and 17 skipped. It ran 80 of 97 specs with port-forward skipped.

Remaining gaps include host namespaces, per-container PID namespaces, mount propagation, and AppArmor assumptions that conflict with a MicroVM-per-pod architecture. The baseline shows meaningful CRI coverage; it is not a claim that Box 3.2.0 has complete Kubernetes CRI conformance.

## Install

Linux or macOS:

```bash
curl --proto '=https' --tlsv1.2 -fsSL \
  https://raw.githubusercontent.com/A3S-Lab/Box/main/install.sh | sh
```

Windows x86-64:

```powershell
irm https://raw.githubusercontent.com/A3S-Lab/Box/main/install.ps1 | iex
```

The installers select the platform artifact and verify its SHA-256. Run `a3s-box info` before a workload to confirm virtualization, symbolic-link support, and host capability.

## Choosing a path

- Use the default MicroVM for untrusted work or a dedicated kernel.
- Use the Sandbox preview only for assessed, trusted work on Linux where lower overhead matters.
- For Kubernetes, validate the actual workload against the current CRI guide instead of assuming complete Docker/containerd behavior.
- For a remote multi-tenant product, keep authentication, quotas, and network APIs outside Box.
