A3S Code now has two multi-agent entry points. They solve different problems.

- `task` is model-invoked. One call can start a single task or a concurrent fan-out of 1–32 independent tasks.
- `dynamic_workflow` is registered explicitly by the host. A bounded JavaScript PTC function describes control flow while A3S Flow owns the run history.

Use the first when deciding whether to delegate is part of the model's job. Use the second when steps, retries, and recovery rules must be fixed by the application.

## `task` is the delegation entry point

A3S Code 6.8 consolidated single-task and concurrent delegation into one `task` contract. The former `parallel_task` surface remains only as a hidden compatibility alias.

Delegated work still passes through the current Session's permission, human-confirmation, budget, and cancellation paths. A child task is not a second agent system that bypasses policy.

Typical uses include:

- checking Linux, macOS, and Windows builds at the same time;
- splitting repository exploration, failure reproduction, and review;
- delegating one bounded task with an independently verifiable result.

If the work must survive a process restart or wait for an external callback, a one-shot fan-out is not enough.

## A3S Flow stores workflow facts

A3S Flow 0.4.2 records a run as an append-only event history. `FlowEngine` projects current state from that history instead of treating an in-memory call stack as the source of truth.

Current commands include:

| Command | Purpose |
| --- | --- |
| `ScheduleStep` | Run one side-effecting step and persist its result or failure |
| `ScheduleSteps` | Register a batch of stable-ID parallel steps |
| `WaitUntil` | Suspend until a deadline without holding a worker |
| `CreateHook` | Wait for approval, a webhook, or another external callback |
| `Complete` / `Fail` | Write a terminal result |

Stores are available for memory, JSONL files, SQLite, and PostgreSQL. Another process can continue driving a run from the same history.

One limit matters: the boundary between an external side effect and `StepCompleted` is at least once. If an API call succeeds and the process exits before the result is committed, the step can be delivered again. Step implementations need a stable idempotency key. Flow cannot infer whether a remote system accepted the previous call.

## How Code uses Flow

`DynamicWorkflowRuntime` lets a PTC function return Flow commands. Ordinary script steps may use tools allowed by the current registry. Agent fan-out is scheduled as a host step named `task`. Project-local history is stored under `.a3s/workflow` by default.

```js
async function run(ctx, inputs) {
  if (inputs.kind === 'workflow') {
    return {
      type: 'schedule_steps',
      steps: [
        { step_id: 'tests', step_name: 'task', input: { task: 'Run focused tests' } },
        { step_id: 'review', step_name: 'task', input: { task: 'Review the changed API' } },
      ],
    }
  }

  return { ok: true }
}
```

The example shows the ownership boundary: PTC chooses the next command, Flow stores the history, and Code's `task` runs agent work.

To prevent recursive execution, `program`, `dynamic_workflow`, and the old `parallel_task` alias are excluded from the default script allow-list. PTC also cannot start a direct nested `task` fan-out; parallel agent work must be scheduled as explicit Flow steps.

## A budget is not a billing meter

`session.workflow_with_token_budget(Some(limit))` gives child runs a shared `WorkflowBudget`. In sequential execution, the next model request is denied after the limit is reached.

Concurrent execution can overshoot slightly because several requests may enter the model before usage updates the ledger. This is a soft run-size limit, not an exact per-token settlement guarantee, and it does not terminate requests already in flight.

For tighter cost control, also bound fan-out width, child turns and output, model concurrency, and the provider-side hard quota.

## Which surface to use

| Requirement | Surface |
| --- | --- |
| Let the model decide whether to delegate | `task` |
| Fix phases and loops in host code | `session.workflow()` |
| Persist steps, waits, callbacks, and retries | A3S Flow |
| Run replayable dynamic flows in the TUI | Registered `dynamic_workflow` |

A3S Code owns governed agent execution. A3S Flow owns workflow history and recovery. Keeping those responsibilities separate makes failure behavior much easier to reason about.
