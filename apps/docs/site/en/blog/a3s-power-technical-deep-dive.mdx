A3S Power 0.7.0 is the current stable release. The previous headline—“a 10B model in 256 MB on $10 hardware”—was not a reproducible release guarantee and has been removed.

Power now has three independently selectable surfaces:

| Surface | Use | Network behavior |
| --- | --- | --- |
| `artifact-provisioning` | Install a consumer-owned, revision-locked multi-file model bundle with bounded transfer and digest admission | Opens no listener; HTTPS is used only when the host permits first-use installation |
| `embedded-inference` | Reuse device, weight, admission, and receipt infrastructure from OCR, vision, or language-model crates | Opens no listener |
| Default server | Serve OpenAI-compatible chat, completion, embedding, and model lifecycle APIs | Starts an explicit service |

All three share resource and integrity contracts. Model graphs, tokenizers, pre/post-processing, and quality acceptance remain the responsibility of model-owning repositories.

## Verified artifact provisioning on `main`

The minimal `artifact-provisioning` feature is new on the current `main`
branch. A consumer supplies the immutable model identity, revision, filenames,
maximum byte counts, source URLs, and SHA-256 digests. Power owns HTTPS
transfer, streaming size enforcement, cross-process locking, temporary files,
atomic file commits, deterministic URL-free receipts, and independent offline
reuse checks. It does not choose a model or silently advance a revision.

A3S Code uses this boundary for its default local workspace embedding route.
With `local_cpu {}`, Code fixes the MiniLM/ONNX semantics and hashes while Power
installs the bundle on first use. Users do not need to download or convert ONNX
files. `--offline` and `A3S_NO_AUTO_INSTALL=1` keep a missing first use
read-only, and an explicit artifact manifest remains available for
operator-owned distribution.

## What the embedded runtime owns

The embedded path provides:

- typed CPU, CUDA, and Metal device selection;
- bounded request, session, memory, and device queues;
- SafeTensors identity, verification, replicas, and range reads;
- measurable mmap, cache, and prefetch policies;
- cancellation, cleanup, and canonical execution receipts;
- hardware-evidence structures that omit model input.

It does not embed PP-OCR, document parsing, or another product model. A3S OCR may use Power's weight and device layer while continuing to own its graph and output semantics.

Minimal dependency:

```toml
[dependencies]
a3s-power = { version = "0.7.0", default-features = false, features = ["embedded-inference"] }
```

```rust
use a3s_power::inference::{DevicePreference, EmbeddedRuntime, InferenceLimits};

let runtime = EmbeddedRuntime::new(
    DevicePreference::Auto,
    InferenceLimits::default(),
)?;
```

## The server path

The default server exposes `/v1/chat/completions`, `/v1/completions`, `/v1/models`, and `/v1/embeddings`. Current backends include mistralrs, with optional llama.cpp, picolm, and OpenAI-compatible proxy paths.

picolm uses pure-Rust GGUF layer streaming to keep peak weight residency near one layer at a time. The current project documentation states a “7B+ model in 512 MB TEE EPC” boundary, not the old 10B/256 MB claim. Model, quantization, context length, and target hardware still require a dedicated benchmark.

## What TEE evidence can establish

TEE mode binds a hardware report to a nonce, launch measurement, model digest, runtime policy, and request receipt. The client verifier decides which measurements and evidence it accepts.

```text
model artifact ──hash/signature──┐
runtime policy ──────────────────┼─> canonical claims
request nonce ───────────────────┘         │
                                           ▼
                                  SEV-SNP / TDX report
                                           │
                                           ▼
                                      client verifier
```

RA-TLS can carry attestation in a certificate extension, and inference responses can include request-receipt digests. Strict verification rejects simulated reports and requires the caller to pin an expected measurement.

Support for an ioctl or evidence format is not the same as certification of a production machine. Firmware, certificate chains, boot images, GPU evidence, deployment, and side-channel policy remain part of acceptance.

## Model privacy controls

The current implementation includes model SHA-256 and Ed25519 checks, AES-256-GCM encrypted-model loading, sensitive-buffer zeroization, log-field redaction, and optional token-metric coarsening.

Each addresses a different risk:

- encrypted files protect weights at rest;
- a TEE protects runtime memory under a specific threat model;
- attestation lets a client inspect the environment;
- redaction reduces application-level leakage.

No single item is a blanket guarantee against every host, administrator, hardware attack, or deployment error.

## 0.7.0 versus `main`

Release 0.7.0 added verified SafeTensors range indexes, optional buffered/direct reads, and a standalone storage benchmark. Current `main` continues with verified artifact provisioning, multi-root capacity aggregation, bounded inference queues, a model Session Pool, microbatch plans, and hardware-evidence bundles. Those additions are still under `Unreleased`.

## Deployment checklist

1. Choose the embedded library or the network service deliberately.
2. Keep model semantics and correctness tests in the model repository.
3. Record model, quantization, context, throughput, and peak memory on the exact hardware.
4. Use the strict verifier for TEE deployments; do not ship simulation mode.
5. Pin evidence bundles into a signed release or another trust root. A SHA-256 digest is not a signature.
