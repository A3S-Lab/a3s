A3S Code 现在有两套多 Agent 入口。它们解决的问题不同，不能混为一谈。

- `task` 由模型调用。一次可以启动一个任务，也可以并发启动 1 到 32 个独立任务。
- `dynamic_workflow` 由宿主显式注册，使用受限的 JavaScript PTC 描述控制流，再把运行历史交给 A3S Flow。

前者适合“是否拆任务也交给模型决定”。后者适合步骤、重试和恢复规则需要由程序固定的工作。

## `task` 是委派入口

A3S Code 6.8 把单任务和并发 fan-out 收进了同一个 `task` 契约。模型不再需要在 `task` 与 `parallel_task` 之间选择；`parallel_task` 只作为隐藏的兼容别名保留。

这个入口仍然经过当前 Session 的权限、人工确认、预算和取消链路。子任务不是绕开策略运行的第二套 Agent。

适合 `task` 的例子很直接：

- 同时检查 Linux、macOS 和 Windows 构建；
- 把代码探索、测试复现和安全审查分给不同子任务；
- 只委派一个边界清楚、结果可独立验收的任务。

如果步骤之间存在长期等待、外部回调或进程重启后的恢复要求，单次 fan-out 就不够了。

## A3S Flow 保存工作流事实

A3S Flow 0.4.2 使用追加事件记录一次运行。`FlowEngine` 根据历史投影当前状态，而不是把内存调用栈当成事实来源。

当前命令包括：

| 命令 | 用途 |
| --- | --- |
| `ScheduleStep` | 执行一个有副作用的步骤，并持久化结果或失败 |
| `ScheduleSteps` | 一次登记一组稳定 ID 的并行步骤 |
| `WaitUntil` | 挂起到指定时间，不占用运行线程 |
| `CreateHook` | 等待审批、Webhook 或其他外部回调 |
| `Complete` / `Fail` | 写入终态 |

事件存储可以是内存、JSONL 文件、SQLite 或 PostgreSQL。工作进程退出后，新的进程可以从同一历史继续驱动运行。

这里有一个必须写清楚的限制：外部副作用与 `StepCompleted` 之间是 at-least-once 边界。如果 API 调用已经成功、进程却在结果落盘前退出，步骤可能再次投递。步骤实现要使用稳定的幂等键，Flow 不会替业务系统猜测“刚才是否成功”。

## Code 怎样接入 Flow

`DynamicWorkflowRuntime` 让 PTC 函数返回 Flow 命令。普通脚本步骤可以调用当前注册表中允许的工具；需要并发 Agent 时，则安排名为 `task` 的宿主步骤。运行历史默认写在项目的 `.a3s/workflow` 下。

```js
async function run(ctx, inputs) {
  if (inputs.kind === 'workflow') {
    return {
      type: 'schedule_steps',
      steps: [
        { step_id: 'tests', step_name: 'task', input: { task: 'Run focused tests' } },
        { step_id: 'review', step_name: 'task', input: { task: 'Review the changed API' } },
      ],
    }
  }

  return { ok: true }
}
```

这是示意代码，重点是职责分工：PTC 决定下一条命令，Flow 保存历史，Code 的 `task` 执行 Agent 工作。

为避免递归失控，`program`、`dynamic_workflow` 和旧的 `parallel_task` 别名不会进入脚本默认允许列表。PTC 也不能在脚本内部直接再做一层 `task` fan-out；并行任务要通过 Flow 步骤显式安排。

## 预算不是精确计费器

`session.workflow_with_token_budget(Some(limit))` 会让各个子运行共享一个 `WorkflowBudget`。顺序执行时，达到上限后下一次模型调用会被拒绝。

并行执行时仍可能有少量超额：多个请求可以在账本更新前同时进入模型。这个预算是控制运行规模的软上限，不是逐 token 的结算保证，也不会强行杀掉已经在途的调用。

需要严格成本控制时，应同时限制：

- fan-out 数量；
- 每个子任务的轮次和输出；
- 模型并发数；
- 外部供应商侧的硬额度。

## 现在该怎么选

| 需求 | 入口 |
| --- | --- |
| 让模型决定是否委派 | `task` |
| 宿主代码固定阶段和循环 | `session.workflow()` |
| 需要持久化步骤、等待、回调和重试 | A3S Flow |
| 在 TUI 中运行可回放的动态流程 | 已注册的 `dynamic_workflow` |

A3S Code 负责 Agent 执行和治理，A3S Flow 负责工作流历史与恢复。把这两个边界分开后，故障处理会简单很多。
