A3S Cloud 早已不是旧文章里的 NestJS 示例。当前控制面是 Rust 项目，业务状态放在 PostgreSQL，长任务由 A3S Flow 继续驱动。

这里使用 DDD，不是为了把目录做得复杂，而是为了回答三个问题：谁能改这份状态、一次修改必须保持哪些约束、失败后从哪里继续。

## 模块先按业务边界拆

控制面当前包含 `identity`、`projects`、`workloads`、`fleet`、`edge`、`operations`、`assets`、`agents`、`secrets`、`sources` 等模块。每个模块采用相同的四层结构：

```text
modules/<module>/
├── domain/
├── application/
├── infrastructure/
└── presentation/
```

- `domain` 放实体、值对象、领域规则和仓储接口，不依赖 HTTP 或 PostgreSQL。
- `application` 放命令、查询和处理器，负责一次用例的编排。
- `infrastructure` 实现 PostgreSQL、对象存储、Git 或外部服务适配器。
- `presentation` 把 REST、SSE 或 Management MCP 请求转换成命令和查询。

目录只是结果。真正的边界是：`fleet` 管节点与命令日志，`edge` 管 Gateway 期望状态，`workloads` 管部署意图；它们不能直接修改彼此的表来“省一次调用”。

## 一次部署命令发生了什么

以创建或更新 Workload 为例，控制面大致执行这条链路：

1. Presentation 层解析租户上下文、请求 ID 和幂等键。
2. Command Handler 读取领域对象并校验组织、项目、环境和版本约束。
3. 仓储在事务中写入期望状态、幂等记录和 Outbox 事件。
4. `operations` 创建可追踪的长任务身份。
5. A3S Flow 在请求返回后继续调度、下发节点命令、等待健康证据并处理重试。
6. 查询侧读取投影，REST、CLI、Web 和 Management MCP 看到同一份业务结果。

HTTP 请求不需要等部署结束。它只负责把意图和 Operation 身份可靠地提交下来。

## 幂等不是“重复请求返回 200”

Cloud 的写操作把幂等范围、幂等键和规范化后的请求摘要一起保存。

- 同一个键和同一份请求可以回放原结果。
- 同一个键配上不同请求会返回冲突。
- 节点命令也有稳定身份，Agent 重启后不会凭空创建第二次部署。

这比在 Controller 里做一个内存缓存可靠，因为服务重启和多副本不会丢掉判断依据。

## Outbox 与 Flow 解决的不是同一件事

Outbox 确保“业务事务已经提交”与“需要发布的集成事件”不会分裂。Relay 只发布已经进入数据库的消息。

A3S Flow 则负责有状态的长任务：步骤、等待、重试、Hook、取消和恢复。它不是领域仓储，也不替 Workload 聚合决定版本是否合法。

可以简单记成：

```text
Domain 决定允许发生什么
Repository 原子保存业务事实
Outbox 把已提交事实送出模块
Flow 让长任务跨故障继续
```

## Cloud 没有把所有东西做成事件溯源

Cloud 的权威业务状态仍在 PostgreSQL 表和领域仓储中。A3S Flow 的运行历史采用追加事件，但这不等于每个聚合都必须从事件重放。

对项目名称、环境配置这类普通 CRUD 状态，版本字段、事务和审计已经够用。对部署、构建、节点命令和 Agent 执行这类跨进程流程，持久化步骤历史才有价值。

## 当前交付边界

Cloud 的 `F0` 基础能力已经验证；Box-only 迁移、外部源码交付、控制面、Agent 发布与执行、生产规模等仍按 Roadmap 的 gate 推进。旧 Docker 路径留下的验证结果不能自动证明新的 Box-only 路径。

这也是 DDD 在这个项目里的实际作用：状态归属和完成条件写在模块与 gate 里，不用一篇架构文章把“代码存在”包装成“产品已经交付”。
