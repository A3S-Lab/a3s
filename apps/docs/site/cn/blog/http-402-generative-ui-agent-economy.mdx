HTTP `402 Payment Required` 存在于标准里，但它没有规定报价格式、支付方式、凭证、重试或退款语义。只返回一个 402，Agent 不知道下一步该做什么。

旧版文章把 402、自动支付和生成式 UI 连成了一条已经到来的产品路线，这不够准确。A3S 当前没有实现 x402 或自动支付协议，A3S Gateway 也不会替请求方付款。

## 一个可用的付费协议还缺什么

至少需要定义这些字段和状态：

1. **报价**：资源、金额、币种、有效期和服务身份。
2. **支付方式**：链上、预付余额、企业账户或其他受支持渠道。
3. **请求绑定**：报价必须绑定方法、路径、请求摘要和一次性 nonce。
4. **授权凭证**：服务端能验证，且不能被复制到另一笔请求。
5. **幂等**：重试不能重复扣款，冲突请求不能复用同一个键。
6. **结果与收据**：付款成功不等于业务执行成功，两者要分开记录。
7. **撤销与争议**：过期、取消、退款和部分失败要有明确状态。

这些内容不属于 HTTP 402 本身。不同实现如果不共享同一份契约，仍然无法互操作。

## Agent 不能看到价格就直接付

自主调用者至少要经过三道控制：

- 组织策略允许购买什么；
- 当前任务还剩多少预算；
- 金额、服务身份或风险超过阈值时是否需要人工确认。

支付工具还应与普通网络请求分开。抓取网页时遇到 402，不应自动把响应里的任意地址当作付款目标。

## A3S 当前能做什么

现有项目提供的是底层部件，不是支付产品：

- **A3S Gateway 1.0.12** 可以转发 HTTP、SSE、WebSocket、gRPC、TCP 和 UDP，执行 ACL 路由、鉴权、限流与健康策略。它目前没有 x402 解析器或付款状态机。
- **A3S Code 6.8** 有权限、人工确认、预算和受治理工具调用，可作为未来支付工具的上层控制点，但当前没有内置支付工具。
- **A3S Flow 0.4.2** 能保存步骤、等待、回调、重试和幂等业务 ID，适合承载支付后业务流程，但不会生成或验证支付凭证。
- **A3S UI 0.1** 是语义 HTML、CSS 和小型控制器组成的设计系统。它可以呈现报价和审批界面，但不是“模型实时生成任意 UI”的运行时。

## 如果在 A3S 里实现

一个合理的边界可能是：Gateway 原样保留 402 响应；Code 的受治理工具解析受信任的报价契约；组织策略与用户确认决定是否支付；Flow 用稳定 ID 记录报价、支付和业务重试；UI 只渲染结构化数据。

```text
service ──402 + signed quote──> agent
agent ──policy / budget / approval──> payment tool
payment tool ──receipt──> Flow
Flow ──same idempotency key──> service retry
```

这仍然只是设计建议，不是当前交付声明。真正实现前还需要确定威胁模型、凭证格式、供应商和端到端失败测试。

## 结论

402 有用，因为它给“需要付款”留下了一个标准 HTTP 位置；它不够用，因为支付的大部分语义都在状态码之外。

对 Agent 软件来说，先把授权、预算、幂等和收据做清楚，比先做一段自动付款演示重要。
