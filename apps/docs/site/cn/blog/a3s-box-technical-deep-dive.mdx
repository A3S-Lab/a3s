A3S Box 3.2 是本地 OCI 运行时，不是托管 Sandbox 服务。它提供 Docker-like CLI、跨语言本地 SDK、CRI/containerd 适配器，以及真正启动工作负载的宿主与 guest 组件。

旧文章使用“40MB、200ms、完整替代 Docker”做标题，这些说法掩盖了平台和功能条件。当前项目采用更明确的契约：默认使用独立内核 MicroVM；共享内核 Sandbox 只能由调用方显式选择。

## 两种隔离不会自动互换

| 契约 | 默认 MicroVM | 显式 Sandbox |
| --- | --- | --- |
| 后端 | libkrun | A3S OCI Runtime |
| 内核 | 独立 guest Linux | 共享宿主 Linux |
| 选择方式 | 省略 `--isolation` | `--isolation sandbox` |
| 主要用途 | 不受信任任务、更强租户边界 | 受信任或半受信任工具、测试 |
| TEE / warm pool / snapshot-fork | 合格宿主上可用 | 拒绝 |
| 自动降级 | 从不 | 从不 |

Box 不接受 `--isolation microvm`。省略参数就是唯一公开的默认 MicroVM 选择，避免脚本把后端名当成可随意替换的兼容模式。

```bash
# 默认：MicroVM
a3s-box run --rm alpine:3.20 -- uname -a

# 仅在通过能力检查的 Linux 宿主上显式选择 Sandbox
a3s-box run --rm --isolation sandbox alpine:3.20 -- id
```

## 当前管理面

Box 的 CLI 覆盖：

- `run`、`create`、`start`、`stop`、`exec`、`attach`、`logs` 和 health；
- OCI pull/push、build、save/load、commit 与缓存；
- bind mount、volume、tmpfs、snapshot、copy 与 diff；
- TSI、命名 bridge、TCP 发布和受限 Compose 子集；
- warm pool，以及 Linux/KVM 上可选的 snapshot-fork；
- audit、metrics、events、安全收据和 SEV-SNP 定向的 TEE 流程。

“Docker-like”不等于 Docker API 全兼容。不支持的选项会在状态变更前失败，而不是保存后忽略。

## SDK 使用同一个本地运行时

Rust、Python、TypeScript 和 Go SDK 都操作安装在本机的同一份 Box 状态。它们没有远程 endpoint、域名或 API key 配置。

当前 3.2 SDK bridge 在正常调用前校验 48 项操作清单。协议版本或返回类型不匹配会直接失败。

```python
from a3s_box import Sandbox

with Sandbox.create("python:3.12-alpine") as sandbox:
    result = sandbox.commands.run("python -c 'print(6 * 7)'")
    print(result.stdout)
```

需要远程 Sandbox 服务的产品，应在本地 SDK 前增加自己的认证服务；Box 本身不冒充网络控制面。

## 平台边界

| 路径 | 当前状态 |
| --- | --- |
| Linux/KVM MicroVM | 主要路径；部分受限 egress 已通过真实宿主 gate |
| Apple Silicon/HVF MicroVM | 已实现；部分受限 egress 已通过真实宿主 gate |
| Windows x86_64/WHPX | 已实现并做过 soak；仅 1 vCPU，缺少 exec/PTY、Bridge、TEE、snapshot-fork、CRI |
| Linux Sandbox | Preview；共享宿主内核 |
| Kubernetes | Preview；CRI v1 + containerd runtime-v2 shim |
| TEE | SEV-SNP 定向；TDX 尚未产品化 |

## Kubernetes 证据怎么读

项目记录的最新 `critest` 基线来自 Box 2.2.0：73 passed、7 failed、17 skipped，运行了 97 个 spec 中的 80 个，并跳过 port-forward。

剩余问题包括 host namespace、每容器 PID namespace、mount propagation 和 AppArmor 等 MicroVM-per-pod 架构差异。这个基线说明 CRI 已经能跑很多生命周期和安全测试，但它不等于 3.2.0 已经获得完整 Kubernetes CRI conformance。

## 安装

Linux 或 macOS：

```bash
curl --proto '=https' --tlsv1.2 -fsSL \
  https://raw.githubusercontent.com/A3S-Lab/Box/main/install.sh | sh
```

Windows x86_64：

```powershell
irm https://raw.githubusercontent.com/A3S-Lab/Box/main/install.ps1 | iex
```

安装脚本会选择平台包并校验 SHA-256。运行工作负载前先执行 `a3s-box info`，确认虚拟化、符号链接和宿主能力。

## 该选哪条路径

- 任务不可信或需要独立内核：使用默认 MicroVM。
- Linux 上的受信任工具更看重低开销：明确评估后使用 Sandbox preview。
- 需要 Kubernetes：先按当前 CRI 文档验证自己的工作负载，不要按 Docker/containerd 的全部行为做假设。
- 需要远程多租户服务：把认证、配额和网络 API 放在 Box 之外。
